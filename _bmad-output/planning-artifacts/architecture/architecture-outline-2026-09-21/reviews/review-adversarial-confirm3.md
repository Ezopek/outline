## 3. Detailed findings

### R4-1 (Medium). Summary precedence has no mechanism and contradicts the audit insert rule

**ADs:** AD-7 ("A summary from an attempt that committed, or that observed the committed row, replaces an `aborted_*` or `rejected` summary for the same Event ID, and the reverse never happens"), AD-14 ("persist at most one idempotent summary"; "by `INSERT … ON CONFLICT DO NOTHING` on the Event ID"; "`documentId` is set only when the document row exists"), AD-15, AD-18.

**Pair.**
- *Unit A (the audit-adapter story)* implements AD-14 as written: one summary writer, `INSERT … ON CONFLICT DO NOTHING`. The HTML worker story calls it. Attempt 2 writes `aborted_after_decision`; attempt 1 commits and its `validated` insert is dropped. The audit says aborted for a committed document, which is the R3-1 outcome the precedence rule was written to prevent.
- *Unit B (the worker story)* adds its own `ON CONFLICT (id) DO UPDATE … WHERE data->>'outcome' IN (…)`. Nothing says which columns move. The aborted row has `documentId` null and its own `createdAt`; a replacement that updates only `data` leaves `documentId` null, so the Event is not retrievable by document, and one that replaces `createdAt` moves the row inside the `events(teamId, name, createdAt)` index range. Other audit callers now see two write behaviors.
Both obey AD-7 and AD-14 as worded because each names its own writer.

**Tighten (AD-14).** "The summary write is `INSERT … ON CONFLICT (id) DO UPDATE`, applied only when the stored `data.outcome` is `aborted_*` or `rejected` and the new outcome is `validated`, `validated_with_warnings`, or `degraded_validation`; it replaces `data`, `documentId`, and `collectionId` and keeps `createdAt`. Every other conflict does nothing." AD-18: one fixture each for aborted-then-committed (replaced), committed-then-aborted (unchanged), and rejected-then-committed.

### R4-2 (Medium). "Converts to the committed path" is defined for two cases and used for four

**ADs:** AD-7 (step 0; unique violation; "Before returning or summarizing any non-committed outcome (rows 3, 4, 5), the attempt repeats the lookup, and a found row converts it to the committed path"; "The requester probes … a found row is reported as `committed` (reconstructed as above, or row 7 when no summary exists)"), AD-12 (`validation` shapes), AD-14 (`counts.byCode`, `runtimeFailOpenExercised`).

**Gaps.**
1. *What a converted attempt returns.* "The committed path" is defined for step 0 (reconstruct from the summary) and for a unique violation after the attempt's own persist decision (return the attempt's own `validation`). An attempt converted from row 3 or 4 has no persist decision. Unit A reconstructs. Unit B returns its own `validation`, which yields `kind: "committed"` with `validation.status: "rejected"`, contradicting AD-12 (a rejection is `success: false`). Unit C reconstructs but stops at the first summary it finds.
2. *Reconstruction can read a non-committed summary.* Under the precedence rule the summary present when a converted attempt or the requester reconstructs may be the very `aborted_*` or `rejected` summary awaiting replacement. Reconstruction maps `outcome` to `validation.status`; three of the outcomes have no mapping, and "retrying … if the winner's summary has not landed" has no exit condition for "a summary landed but is not the committed one".
3. *Which summary a converted attempt writes.* Precedence lets a summary from an attempt "that observed the committed row" replace an aborted one. A converted attempt has its own counts and its own `runtimeFailOpenExercised`; writing them records a fail-open exercise for an attempt that did not commit.
4. *`counts.byCode` holds Finding codes too.* AD-14's shape counts errors, warnings, and System Failures by code. "`systemFailures` is rebuilt from `counts.byCode` (one entry per counted code …)" read literally turns `DISCOURAGED_MARKDOWN_STRUCTURE` into a System Failure on a reconstructed `validated_with_warnings`.
5. *Coverage.* The repeated lookup lists rows 3, 4, 5 but not row 2 (`conflict`); the requester probe covers `aborted` and no result but not `rejected` or `conflict`.

**Tighten (AD-7).** "A found row is always reported through one routine, `committedFromSummary(invocationId)`, except after the attempt's own persist decision (a unique violation), which returns the attempt's own `validation`. The routine waits up to the probe bound for a summary whose outcome is `validated`, `validated_with_warnings`, or `degraded_validation`; an absent or non-committed summary at the bound is row 7. `systemFailures` are rebuilt only from `byCode` entries whose code is a System Failure code. An attempt converted from row 2, 3, 4, or 5 writes no summary. The repeated lookup and the requester probe cover every non-committed result (`conflict`, `rejected`, `aborted`, no result)."

### R4-3 (Medium). Blob ownership after per-attempt tracking

**ADs:** AD-7 ("Each attempt tracks and deletes only the blobs it staged, and Attachment IDs are pre-allocated per attempt; AD-20 rows 2, 3, 4, and 5 delete them idempotently, except that a unique violation on the pre-allocated `documentId` is the `committed` path below and never deletes blobs; row 7 never deletes them"; "Document content is passed by staged reference"), AD-20, D-9.

**Baseline facts.** `DocumentImportTask.perform` deletes its staged `key` in a `finally` (`DocumentImportTask.ts`, the `finally { if (key) … deleteFile(key) }` block); the baseline requester passes content in memory, so the fork's staged-reference input is new.

**Pair.**
- *Loser's blobs.* The carve-out predates per-attempt tracking; under it, the loser's blobs belong to a rolled-back attempt whose Attachment rows never existed. Unit A follows the carve-out and leaks them: a non-crash orphan that D-9's crash sweeper does not describe. Unit B deletes them (safe, because IDs and keys are per attempt) and contradicts the sentence.
- *Source content.* The blob staged by the requester is not staged by any worker attempt, so "each attempt deletes only what it staged" does not cover it, and rows 2 to 5 delete "the blobs" without naming it; row 6 deletes nothing; row 7 never deletes. Unit A reuses the baseline conversion code with its `finally` delete: a redelivered or concurrent second attempt then fails to read its input and reports row 3 (a summary that R4-1's mechanism must later replace). Unit B has the requester delete on a terminal result: a slow ghost attempt loses its input. Unit C deletes nothing: one leaked object per HTML create.

**Tighten (AD-7).** "A unique-violation attempt deletes the blobs it staged, because its transaction rolled back. The requester-staged source content belongs to the invocation: the requester deletes it before `queue.add` on a requester-determined row 3; otherwise the worker deletes it when it returns a terminal outcome (`committed`, `rejected`, `conflict`, `aborted`) after its repeated lookup; the baseline conversion code's own delete is disabled for the enforced task; a row 7 leaves it, and an attempt whose input is gone is row 3."

**ADs:** AD-11 ("a failure of one rule kind yields one System Failure per (unit, code), located at its document (AD-4)", "On every surface"), AD-4 ("`documentId` names the document of a `document` scope or of a failed document unit"; "For a create, the projection's pre-allocated document ID is the `documentId` of every location"), AD-12 ("a failure of one document unit is located `scope { scopeKind: "document", documentId, collectionId? }`"; "Both rejection kinds locate their System Failure as `scope { scopeKind: "collection", collectionId? } … and so does every other System Failure of an enforced write"), AD-7 (reconstruction uses "collection scope location").

### R4-5 (Medium). The 63 s invariant depends on bounds nothing enforces

**ADs:** AD-11 ("The sum of the code-owned bounds on any surface, including the 2-second commit probe inside the persistence budget, is at most 63 seconds"; the validation deadline "starts … when the enforcement transaction opens"; "Deadlines are checked between units, and a synchronous parse is not preempted"), AD-20 ("probes on a fresh connection within a code-owned bound"; the probe "runs in a short transaction with `SET LOCAL statement_timeout` at the 2-second probe bound"; "client-side timeouts" as a connection-level shape), AD-7.

**Baseline facts.** The pool is `acquire: 30000`, `max` from `DATABASE_CONNECTION_POOL_MAX` (default 5) (`database.ts:57,167-169`). `dialectOptions` sets `application_name` and `ssl` only, so no client-side query timeout exists. The transaction wrapper issues `SET LOCAL statement_timeout` only after the connection is acquired and `BEGIN` has run. `server.setTimeout(REQUEST_TIMEOUT)` (`main.ts:146`) is the socket idle timeout the `/mcp` override replaces.

**Pair, term by term.**
1. *Connection acquisition.* The enforcement transaction, the COMMIT probe, the found-row lookups, and the P0/P1 queries all acquire from a five-connection pool before any `SET LOCAL` exists. P2's 30 s ends before the transaction opens and the 9 s deadline starts after `BEGIN`. Unit A charges acquisition to nothing; Unit B charges it to P2. Under Unit A the write path is 2 + 30 + 30 + 9 + 9 + 3 + 2 = 85 s. Pool pressure is realistic here: serialized enforced writes hold a connection for up to 18 s, a `lint_wiki` snapshot for up to 60 s, and the probe is needed exactly when the database is unhealthy.
2. *`commit()` client side.* A `statement_timeout` is server-side. On a black-holed connection `commit()` neither resolves nor rejects until the OS gives up, so row 7 is never reached and the request runs into the 65 s override: a transport abort for a possibly committed write, which AD-11 `Prevents`. Unit B wraps `commit()` in a timer; Unit A does not. AD-20 names "client-side timeouts" as a shape but assigns no one to create one.
3. *Probe bound.* "Within a code-owned bound" and "`SET LOCAL statement_timeout` at 2 seconds" bound the statement, not acquisition or `BEGIN`. Also unstated: whether P7/P8 statement timeouts are set to the 9 s remainder or to 7 s (the budget less the 2 s probe reserve). Unit A's P7 can end at 9 s and start a probe that the budget does not cover.
4. *`lint_wiki`.* 60 + 3 = 63 assumes the stop is exactly at 60 s. The deadline is checked only between units and before snapshot batches; one unit can be a 1 MiB document (AD-16) evaluated synchronously. Result assembly (sorting and serializing up to 5,000 documents of Findings) has no bound; the 2 s assembly bound is stated for writes only.

**Tighten (AD-11, AD-20).**
- "Connection acquisition for any shell-issued transaction, probe, or lookup is charged to the phase it serves; the enforcement connection is acquired and `BEGIN` issued within P2's 30 s, and expiry is row 3."
- "`commit()` and the probe run under a wall-clock timer equal to the remaining persistence budget (the probe under the 2 s bound, acquisition included); expiry of either is connection-level. P7 and `commit()` statement timeouts are set from the budget less the 2 s probe reserve."
- "`lint_wiki` stops starting new units when less than a code-owned margin (chosen from AD-17's measured maximum unit time) remains, and result assembly is charged to that margin."

### R4-6 (Medium). Arithmetic and scope of the HTML tail, P0/P1, and the persist guard

**ADs:** AD-7 (`deadlineAt`; requester probe; "reconstructed as above" including the retry; the persist guard), AD-11 (P0/P1 "bounded at 2 seconds in total"; invariant of 63 s), AD-8 ("`read_only` and unconfigured writes retain baseline behavior").

1. *HTML tail.* P0/P1 2 s + `deadlineAt` window 56 s (30 + 9 + 9 + 3 + 5) = 58 s. After `deadlineAt` the requester probes (up to 2 s), reconstructs with the "up to the probe bound" retry (up to 2 s), and assembles (up to 2 s): 64 s. The spine states 63. Unit A follows each bound and reaches 64; Unit B trims the requester's reconstruct retry to keep the stated invariant. The socket override (65 s) is not breached on paper, but a one-second margin absorbs every unenforced term in R4-5.
2. *P0/P1 scope.* P0 (lookups, handler-level authorization) runs before classification, so a 2 s bound on "P0 and P1 in total" applies to every write, including unconfigured and `read_only` ones, whose behavior must stay baseline. Unit A wraps the handler prelude in a 2 s timer for all writes; Unit B checks elapsed time at classification and only for an enforced write. AD-20 row 1 says P0 failures keep "baseline behavior", which has no 2 s bound.
3. *Persist guard.* "The worker does not enter the persist step unless the time remaining until `deadlineAt` covers the persistence budget." `deadlineAt` includes the audit bound and the grace. A worker entering P7 with exactly 9 s left commits at `deadlineAt`; its audit lands up to 3 s later, after the requester's probe and reconstruction, so the requester reports row 7 for a committed write. In the normal case the guard cannot fire (30 + 9 < 56 − 9), so this is unreachable, but the guard is then dead text, and AD-18 has no fixture for it.

**Tighten (AD-7, AD-11).** Count the requester's post-`deadlineAt` probe, one reconstruct read, and assembly explicitly in the invariant and lower the requester's retry to zero (the worker's step-0 retry stays); or state the invariant as "at most 64 s" and move the override floor to 66. State that the P0/P1 bound is a check of elapsed handler time at classification for an enforced write only. Change the guard to "covers the persistence budget plus the audit bound".

### R4-7 (Medium). Lock order: creates are unspecified, and collection-then-document forms a cycle

**ADs:** AD-8 ("locks, in this order, the classified collection (`NO_KEY_UPDATE`, for every enforced update, publication, or unpublication … matching the baseline mover's order so the two cannot deadlock) and then the update document row (`FOR UPDATE`); a create takes no parent lock. Enforced writes to one collection are thereby serialized"), AD-20 P3/P7.

**Baseline facts (verified).** `documentCreator` inserts the document (with `parentDocumentId`) and then, for `publish: true`, calls `Document.publish`, which takes the collection `NO_KEY_UPDATE` lock (`Document.ts` publish, around line 1257). `documents.parentDocumentId` carries `documents_parentDocumentId_fkey` (migration `20191119023011`), so the child insert takes `FOR KEY SHARE` on the parent row; `FOR KEY SHARE` conflicts only with `FOR UPDATE`. `documentUpdater` itself locks the document `FOR UPDATE` when a transaction exists (`documentUpdater.ts:114-126`), and the baseline `updateCollectionStructure` hook then takes the collection lock for a title, icon, or color change (document, then collection). `documentCollaborativeUpdater` takes only the document row (`FOR UPDATE`, `hooks: false`), so it cannot join a cycle with the collection lock.

**Pair 1, creates.** The sentence lists updates, publications, and unpublications for the collection lock and says a create takes no *parent* lock. Unit A reads "Enforced writes to one collection are thereby serialized" and has creates take the collection lock at P3. Unit B has creates take no collection lock until `Document.publish` takes it in P7. Contention then surfaces at P3 (row 3, `aborted_before_decision`, charged to the 9 s validation deadline, possibly ending as a fail-open `VALIDATION_TIMEOUT`) under A and at P7 (row 5, `aborted_after_decision`, after a passing decision) under B.

**Pair 2, deadlock.** Enforced update U of document D (collection C, published): lock C, then D `FOR UPDATE`. Child create V under D with `publish: true` (enforced or not): insert takes `KEY SHARE` on D, then `publish` requests C. Interleaving: V inserts; U locks C; U requests D and waits on V's `KEY SHARE`; V requests C and waits on U. PostgreSQL aborts one after `deadlock_timeout`. The window is milliseconds but the workload (an agent updating an index page while creating child pages under it) makes it reachable. The victim is U (row 3 or 5) or V, which may be a baseline UI create that then fails with a deadlock error, and the Sequelize `retry: { match: [/deadlock/i] }` cannot recover an aborted transaction. Before the round-3 change, content-only enforced updates took no collection lock, so this cycle did not exist. The same shape arises between U and a baseline `documents.update` of the same document with a title change (document, then collection).

**Tighten (AD-8).** (1) "A create takes the classified collection's `NO_KEY_UPDATE` lock first, like every other enforced write" (or state that it does not and that contention appears as row 5). (2) "The document row is locked `FOR NO KEY UPDATE`, and the writer's own `FOR UPDATE` re-lock is removed or downgraded, because a child insert holds `KEY SHARE` on its parent and conflicts only with `FOR UPDATE`; enforced writers still serialize against each other and against the collaborative updater's `FOR UPDATE`." (3) Record the residual: enforced collection-first writers can deadlock with baseline document-first writers (UI or API title change); the victim of an enforced write is row 3 or 5. AD-18: a fixture for child create against enforced update of the parent.

### R4-8 (Medium). Open-mode fail-open eligibility is still steerable

**ADs:** AD-13 ("In an `open` collection, `VALIDATION_TIMEOUT` and `VALIDATION_RUNTIME_FAILED` are fail-open eligible only when the projected document is within the AD-16 per-document Markdown and link-reference limits … so an actor cannot elect to skip linting by shaping content"), AD-16 (the limits; "the per-document numbers also bound fail-open eligibility"), AD-11 (row 3 below the floor on entering P5; the floor is "left to the story"; P3 lock wait is charged to the 9 s), AD-8 (per-collection serialization).

**Pairs.**
1. *There is no per-document link limit.* AD-16 lists 5,000 documents, 1 MiB per document, 64 MiB total, 100,000 internal-link references, 10,000 structure nodes; only the 1 MiB figure is per document, and 100,000 is a snapshot total. Unit A applies 100,000 to one document; Unit B has only the size limit. A 1 MiB document can hold well over 100,000 link references.
2. *Measurement and the unknown count.* The core supplies the link count; if link extraction is what raised `VALIDATION_RUNTIME_FAILED`, the count does not exist. Unit A treats an unknown count as ineligible; Unit B as eligible. The "one pure decision function" (AD-13) also gains a third input (within limits) that its inputs, "the validation result with the immutable post-operation collection policy", do not list.
3. *Limits are not sized for the 9 s budget.* The AD-16 numbers were chosen for snapshot totals. AD-17 measures `lint_document` only up to 128 KiB documents with eight links on average. A document at 90,000 unique link targets is 180 batches of 500 inside a 9 s budget shared with P3 and P4; on a slow database it times out inside the limits, and an `open` collection persists it unvalidated.
4. *Lock-queue wait.* P3 lock wait shares the deadline with P5, and the floor for entering P5 is undefined. An actor fires a slow enforced write W1 (holding the collection lock for its whole P3 to P8 span, now that writes serialize) and, right behind it, the payload W2 with several thousand links. W2 acquires the lock with a remainder just above the floor, enters P5, times out on its first batches, and in an `open` collection persists as `degraded_validation`. R3-5's row 3 rule only catches a remainder below the floor.

**Tighten (AD-13, AD-16, AD-11).** (1) "The fail-open size limits are two code-owned write-eligibility constants, a Markdown byte length and a link-reference count of the projected document, sized from AD-17's measured maxima; they are not the AD-16 snapshot caps. When either measure cannot be produced, the document is treated as beyond the limits." (2) "`VALIDATION_TIMEOUT` is fail-open eligible only if P5 began with at least half of the validation deadline remaining; otherwise the shortfall is row 3." (3) List "within limits" as an explicit input of the decision function. AD-18: fixtures for a lock-queued write entering P5 below the threshold and for a document at the eligibility limit.

## 4. Attacked and found closed (no finding)

- **Stale collection lock when the document moved.** The lock is taken on the classified collection before the document lock; if the document moved in between, the post-lock re-fetch shows another collection and the attempt ends as row 2. A concurrent mover of the document or an ancestor blocks on the same collection lock. No pair.
- **Collaborative saves.** `documentCollaborativeUpdater` takes only the document row (`FOR UPDATE`, 15 s `lock_timeout`, `hooks: false`) and never a collection lock, so the collection-first order cannot deadlock with it. The manual `revisionCount` bump is inside the document lock and consistent with the unchanged-update check.
- **Lookup-first versus re-authorization.** The pre-allocated ID is server-generated per request, so a found row can only be this invocation's own commit; the requester rebuilds the response through an actor-scoped load.
- **Cancellation versus the baseline `beforeFind` hook.** `requestContextMiddleware` is applied to `/api` (`routes/api/index.ts:61`), not to `/mcp`, so `assertConnectionOpen` does not fire on MCP requests and does not contradict "cancellation is honored only before the persist decision".
- **Server-reported COMMIT criterion.** An ErrorResponse is emitted by the backend that has finished or aborted the transaction, so the fresh-connection probe sees the final state; the only unsound case is a connection-level failure, which the spine already sends to row 7.
- **Environment transport of the policy file.** A 64 KiB limit is below the Linux per-string limit even with base64; NUL cannot occur in a valid file.
- **AD-13 matrix versus AD-12 statuses and AD-3 Surfaces.** A beyond-limits write in an `open` collection is a fail-closed rejection with `runtimeFailOpenExercised: false`; `VALIDATION_RESOURCE_LIMIT_EXCEEDED` stays `lint_wiki`-only. Consistent (the eligibility measure is R4-8).
- **AD-4 sort keys with `documentId` on scope locations.** Absent values sort last within the derived collection; no ordering ambiguity results (the shape gap is R4-4).
- **Batches and `SET LOCAL` placement (R3-3).** Consistent with PostgreSQL's savepoint rollback of GUC values; no pair.
