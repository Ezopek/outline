### Medium

**M4-1 — AD-14 says audit rows are inserted `ON CONFLICT DO NOTHING`, while AD-7 requires a committed attempt's summary to replace an aborted or rejected one for the same Event ID (AD-14 L254 vs AD-7 L120).**
- AD-14 L254: "by `INSERT … ON CONFLICT DO NOTHING` on the Event ID". AD-7 L120: "A summary from an attempt that committed, or that observed the committed row, replaces an `aborted_*` or `rejected` summary for the same Event ID, and the reverse never happens." Memlog L61 (round 2, "insert-if-absent summary") and L63 (round 3, precedence) differ the same way; L63 supersedes, but AD-14 was not updated.
- Two implementers: A follows AD-14 (first writer wins). A stalled-job second attempt that aborts writes `aborted_after_decision` first, the committing attempt's `validated` row is dropped, and the audit shows an aborted attempt for a committed document, the outcome AD-20 `Prevents` names ("a committed write presenting as a failure"). B follows AD-7 (conditional overwrite) and gets the opposite.
- Fix: AD-14 L254: "by `INSERT … ON CONFLICT (id) DO UPDATE` that overwrites the row only when the stored `outcome` is `aborted_*` or `rejected` and the incoming `outcome` is `validated`, `validated_with_warnings`, or `degraded_validation` (otherwise the insert does nothing); the overwrite also sets `documentId`." Update the memlog L61 clause as superseded.

**M4-2 — The location of a System Failure that belongs to one document unit is stated three ways (AD-4 L94, AD-11 L168, AD-12 L175 and L202).**
- AD-11 L168: "On every surface ... a failure of one rule kind yields one System Failure per (unit, code), located at its document (AD-4)". AD-12 L175: "a failure of one document unit is located `scope { scopeKind: "document", documentId, collectionId? }`". AD-12 L202: "Both rejection kinds locate their System Failure as `scope { scopeKind: "collection", collectionId? }` ... and so does every other System Failure of an enforced write."
- Conflict A (enforced write): a write's rule-kind failure under a savepoint (the fail-open path, `degraded_validation`) is a document-unit failure per L168/L175 (`scope{document, documentId}`) and "every other System Failure of an enforced write" per L202 (`scope{collection}`, no `documentId`). The two locations sort differently (AD-4 sorts on document ID) and the AD-4 sentence "For a create, the projection's pre-allocated document ID (AD-7) is the `documentId` of every location" contradicts L202's collection scope.
- Conflict B (`lint_document`): AD-4 L94 says "`documentId` names the document of a `document` scope", while AD-12 L175 locates a run-wide failure as `scope { scopeKind }` (no `documentId`) and the generic sentinel failure as `scope { scopeKind: "document" }` "without `collectionId`" (no `documentId`). The one unit of a `lint_document` run is the document, so the run-wide and unit-level forms are indistinguishable.
- Fix: AD-12 L202: "... and so does every other run-wide System Failure of an enforced write; a failure of the write's document unit is located as in the document-unit rule above." AD-4 L94 and AD-12 L175: "every `scope` location whose `scopeKind` is `document` carries `documentId`" and reword the run-wide sentence to "`scope { scopeKind }` (plus `collectionId` for a collection-scoped request, plus `documentId` for a document-scoped request)".

**M4-3 — "The committed path" is defined two ways, and one of them cannot be applied to the outcomes AD-7 sends into it (AD-7 L114, L118).**
- L114/L118 use "the `committed` path" both for a unique violation ("returns `committed` with the attempt's own `validation`") and for a found row at step 0 ("`validation` is reconstructed from the audit summary recorded for `invocationId`", "`status` is authoritative"). Then: "Before returning or summarizing any non-committed outcome (rows 3, 4, 5), the attempt repeats the lookup, and a found row converts it to the committed path."
- A row-4 attempt's own `validation` has `status: rejected`; a row-3 attempt has no `validation`. Returning `kind: committed` with either violates AD-12 (a committed write is a success with a `validated*` or `degraded_validation` status; a rejection is `success: false`). If the conversion reconstructs from "the audit summary recorded for `invocationId`", that summary may be the other attempt's `aborted_*` or `rejected` row (M4-1), from which no valid status is reconstructible, and the text does not say to treat it as absent.
- Fix: "A found row converts a row 3, 4, or 5 outcome to the step 0 reconstruction. Reconstruction reads only a summary whose `outcome` is `validated`, `validated_with_warnings`, or `degraded_validation`; any other stored outcome is treated as not yet landed (retry up to the probe bound, then row 7). Only a unique violation after the attempt's own persist decision returns the attempt's own `validation`."

**M4-4 — Per-attempt Attachment IDs and per-attempt cleanup contradict the "never deletes blobs" exception, and the exception leaks the loser's blobs (AD-7 L114).**
- L114: "Each attempt tracks and deletes only the blobs it staged, and Attachment IDs are pre-allocated per attempt; AD-20 rows 2, 3, 4, and 5 delete them idempotently, except that a unique violation on the pre-allocated `documentId` is the `committed` path below and never deletes blobs". The same sentence group says blobs are "tracked under `invocationId`".
- With IDs and storage keys per attempt, the winner's committed Attachment rows reference the winner's blobs; a losing attempt's transaction, including its Attachment rows, rolled back, so its own staged blobs are unreferenced. "Never deletes" leaves them behind, and D-9 defers only "blobs orphaned by a process crash". An implementer who reads "deletes only the blobs it staged" deletes them; one who reads the exception literally leaks them. The "tracked under `invocationId`" wording also suggests a shared list.
- Fix: "On the unique-violation path the attempt deletes the blobs it staged, never blobs staged by another attempt", and "tracked under `invocationId` and attempt". (If Attachment IDs are meant to be invocation-deterministic, say so and keep the exception; the current text says the opposite.)

**M4-5 — The 63-second ceiling omits the HTML requester's post-`deadlineAt` probe and reconstruction retry, and the worker cannot measure "from classification" from the intent it is given (AD-7 L116-L122, AD-11 L168).**
- L122: `deadlineAt` = classification + 30 + 9 + 9 + 3 + 5 = classification + 56 s. L168: P0/P1 2 s, post-commit assembly 2 s, "The sum of the code-owned bounds on any surface, including the 2-second commit probe inside the persistence budget, is at most 63 seconds".
- L120: "Before reporting an `aborted` result or no result for an HTML create, the requester probes the pre-allocated `documentId`; a found row is reported as `committed` (reconstructed as above ...)"; L118: reconstruction retries "for up to the probe bound". Neither the requester's probe query nor the retry is bounded in AD-7 or counted in AD-11. Worst case for a stalled worker: 2 (P0/P1) + 56 (to `deadlineAt`) + 2 (probe) + 2 (retry) + 2 (assembly) = 64 s, which exceeds the stated 63 s and leaves 1 s to the 65 s override (the other surfaces are lint_wiki 63, Markdown write 55, HTML without the tail 60).
- L122 says the worker "measures the preparation bound from classification", but the intent (L116) carries `handlerEnteredAtEpochMs` (tool entry) and `deadlineAt`, not a classification stamp; the worker can only derive it by subtracting the 56 s constant from `deadlineAt`.
- Fix: in AD-11 add "The HTML requester's post-deadline probe and reconstruction share one 2-second bound counted in the sum", restate the ceiling as 64 s (or reduce the grace to 1 s so it stays 60 s), and either add a `classifiedAtEpochMs` field to the AD-7 intent or say the worker derives classification as `deadlineAt` minus 56 s.

**M4-6 — AD-13's fail-open eligibility test refers to a "per-document link-reference limit" that AD-16 does not define (AD-13 L221, AD-16 L286).**
- AD-13 L221: "fail-open eligible only when the projected document is within the AD-16 per-document Markdown and link-reference limits". AD-16 L286: "Code-owned hard limits are 5,000 documents, 1 MiB UTF-8 Markdown per document, 64 MiB total Markdown, 100,000 internal-link references, and 10,000 authoritative structure nodes ... the per-document numbers also bound fail-open eligibility on writes (AD-13)." Only the 1 MiB figure is per-document; 100,000 is a `lint_wiki` snapshot total (memlog L39 "100,000 internal link refs" is the same total).
- Two implementers: one tests only the 1 MiB size; the other applies 100,000 to a single document's link count. This number decides whether an `open` collection may persist unvalidated content, the concern in AD-11's `Prevents` line ("a write path with no deadline whose value decides fail-open admission").
- Fix: state the test once in AD-13 and reference it from AD-16: "eligible only when the projected document's Markdown is at most 1 MiB and its internal-link references are at most 100,000" (or drop the link criterion).

**M4-7 — AD-8's "Enforced writes to one collection are thereby serialized" is false for creates and contradicts AD-7's "stay unserialized" (AD-8 L129, AD-7 L118).**
- L129: the collection lock is taken "for every enforced update, publication, or unpublication ... ; a create takes no parent lock. Enforced writes to one collection are thereby serialized for the span of the transaction." Creates take no collection lock up front (baseline `Document.publish` takes `NO_KEY_UPDATE` on the collection only inside persistence, `server/models/Document.ts:1252-1258`, so a draft create never takes it). AD-7 L118: "Two live attempts for one `documentId` stay unserialized", which is a create.
- An HTML-worker author who reads AD-8's general sentence may drop the AD-7 probes and unique-violation handling as unnecessary; one who reads the parenthetical keeps them.
- Fix: L129: "Enforced updates, publications, and unpublications within one collection are thereby serialized for the span of the transaction; creates are not."
